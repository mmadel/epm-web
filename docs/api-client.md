# Generating the API client

Every request and response type in this workspace is generated. Nothing here describes a
server shape by hand — not an interface, not a field name, not an enum. There is one
description of the API and it belongs to the API.

This document is how you get new models into the workspace when the backend grows some,
and what to do when that goes wrong.

## Where the models come from

```
epm-service controllers
        │  generated by the backend (T-84)
        ▼
   openapi.json
        │  published as a versioned npm package (T-90)
        ▼
@mmadel/openapi-spec@0.2.0          ← pinned in package.json, exactly
        │  openapi-generator, typescript-angular (T-85)
        ▼
projects/api-client/src/generated/  ← committed
```

Two properties of that chain are deliberate and worth not undoing:

**The specification arrives as a pinned version.** Not a fetch, not a copy. So an API
change cannot appear underneath you between one checkout and the next: it appears when
somebody raises the pin, in a commit, with a diff to read. Before ticket `T-91` the
specification was a file copied into this repository by hand — which looked like a pin
and guaranteed none of it, because nothing recorded which backend the copy came from or
whether it was still current. It had, in fact, gone stale.

**The generated client is committed.** So a clean checkout builds without a JVM, a
server shape change is visible in review as a diff, and generation never happens during
a build — a build that needs the network fails on a plane and in a locked-down runner.
CI keeps the committed output honest by regenerating it and insisting the result is
byte-for-byte identical.

## Getting new models

When the backend adds an endpoint or a model, it lands here as a version bump. Three
commands:

```bash
npm i -E @mmadel/openapi-spec@<new version>   # -E: exact. Never a range
npm run generate:api
npm run build
```

Then commit **`package.json`, `package-lock.json` and the regenerated client together**.
They are an input and its output; a commit carrying one without the other is exactly the
state CI's staleness check exists to reject.

### What each step is for

1. **`npm i -E`** replaces the pin. The `-E` matters: without it npm writes `^1.2.3`, and
   a range means two developers install two specifications a fortnight apart and generate
   two different clients, with the difference attributed to whoever pushed second.
   `npm run lint` fails on a range, so this is caught rather than discovered.

2. **`npm run generate:api`** wipes `projects/api-client/src/generated/` and regenerates
   it from `node_modules/@mmadel/openapi-spec/openapi.json`. It prints the version it
   generated from — the one fact that says which API this client now describes, and
   otherwise invisible in the output. The wipe is what makes a **removed** operation
   disappear; a generator only ever writes files, so without it a deleted endpoint's
   service would sit in the tree for ever, absent from a fresh generation and invisible
   to `git diff` because nothing touched it.

3. **`npm run build`** is where a breaking change surfaces, as compile errors naming
   every line that used the old shape. This is the point of the whole arrangement. A
   renamed field is a red build in the commit that renamed it, not an `undefined`
   reaching a patient's screen.

### Reading the diff

The regeneration diff is the API change, so read it as one:

- **New files under `model/`** — new models. Nothing to do; they are exported already.
- **New files under `api/`** — new operations, as injectable services.
- **A field that changed name or type** — the build will name every use.
- **A deleted file** — an operation or model the backend removed. Anything still calling
  it stops compiling, which is the intended outcome.

Everything generated is re-exported by `projects/api-client/src/public-api.ts`, so
screens import from `api-client` and call the generated methods directly. There is no
wrapper and no facade by design: a hand-written type over a generated one is a second
description of the API, and the second description is the one that goes stale. The
`epm/no-server-type-mirrors` lint rule fails the build for it.

## Prerequisites

**A registry token.** The specification is published to GitHub Packages, which
authenticates every read. Export a classic personal access token with `read:packages`:

```bash
export NODE_AUTH_TOKEN=<token>            # bash
$env:NODE_AUTH_TOKEN = "<token>"          # PowerShell
```

A `preinstall` guard stops with a message naming the variable when it is unset — but only
when npm does not have to reach the network first. **`npm ci` downloads dependencies
before it runs `preinstall`**, so on a cold cache the registry's 401 arrives first and the
guard never runs. That is why CI runs the same check as a step before `npm ci`, and why
the 401 row below exists. In CI the value is the `PACKAGES_READ_TOKEN` secret.

**A JDK, 17 or newer.** openapi-generator runs on a JVM. Only `npm run generate:api`
needs it — building and testing the committed client do not, which is the point of
committing it.

## When it goes wrong

| What you see                                                         | What it is                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[check-packages-token] Stopped: NODE_AUTH_TOKEN is not set`         | Exactly what it says. Export the variable; the install never reached the network                                                                                                                                                                                          |
| **401** from `npm.pkg.github.com`                                    | `NODE_AUTH_TOKEN` is unset, empty, or revoked — npm resolved `${NODE_AUTH_TOKEN}` to nothing and authenticated with nothing. This is the most common failure by far, and it reaches you unadorned because `npm ci` fetches before `preinstall` can object                 |
| **404** on a package that is published                               | The token authenticated but cannot read that repository's packages. Check it is a **classic** token with `read:packages`, and not the automatic `GITHUB_TOKEN` — that one reads only its own repository's packages, and the specification is published from `epm-service` |
| A token in `~/.npmrc` is ignored                                     | By design. The committed `.npmrc` sets the same key for this registry and a project's configuration beats the user's. Use the environment variable                                                                                                                        |
| CI: _the pinned specification and the committed API client disagree_ | The client was not regenerated, or not committed alongside the bump. Run `npm run generate:api` and commit the result                                                                                                                                                     |
| `npm run lint` rejects the dependency                                | The pin is a range, or a token literal reached a tracked file. If it is the latter, remove it **and rotate it** — it stays readable in the history whatever the next commit does                                                                                          |
| The generator fails mentioning `java`                                | No JDK on the path. See the prerequisites above                                                                                                                                                                                                                           |

## What not to do

**Do not edit anything under `projects/api-client/src/generated/`.** The next generation
overwrites it, and CI fails the commit that tries. If the generated output is wrong, the
cause is the generator's pinned version or its options in `openapitools.json`, or the
specification itself — and if it is the specification, it is wrong in a backend
controller, not here.

**Do not hand-write the types instead.** A type written here describes the API this
workspace imagines rather than the one the server runs. That fails at runtime, with the
build having been green — worse than having no types at all.

**Do not regenerate during a build.** Generation needs the registry and a JVM. Wiring it
into `prebuild` would make every build need both.

**Do not use a version range to avoid bumping by hand.** Bumping by hand is the feature.
It is the moment somebody reads an API change.
