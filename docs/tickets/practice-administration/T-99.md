**No `Status` row.** Status lives in `BOARD.md` (`WORKFLOW.md`).

**The rule already holds; only its coverage is narrow.** `T-97` enforces it by a test over two folders —
`ui` and `staff/src/app`. This ticket makes it a workspace rule so a third app cannot be added outside it.

---

## 2. Goal

A presentational component cannot reach the API, and nobody discovers that by reading a review comment.

---

## 3. Scope

### In

- A lint rule replacing `T-97`'s two-folder test
- Applied across every project in the workspace, not a named list
- A fixture proving it fails on a deliberate violation
- The old test removed, not left beside it

### Out

- Any component change. **If the rule fails on existing code, that is a finding to raise, not to fix here**
- Other boundary rules — `staff` importing `platform`, and so on. §10
- Anything about `platform`'s own structure

---

## 4. Contract

**Frontend.** `None.` No component, no screen, no route.

**The rule.** A value import of `api-client` from anywhere in `projects/ui/` fails the build. Type-only
imports are the question in §10.

**This ticket must produce no diff under `projects/*/src/`** other than deleting the superseded test.

---

## 5. Logic

**Frontend.**

**The rule is on the folder, not on a list of files.** A list goes stale the first time a file is added.

**It fails the build, not the review.** `T-97` established that design constraints in this workspace are
build-failing — this is the same class.

**Why the boundary exists:** `ui` is presentational and shared. A component that fetches cannot be
rendered in a test, a second app, or a story without a server. The call belongs in a `staff` container.

---

## 6. Data

`No table created, altered or dropped. No migration.` No server call.

---

## 7. Acceptance criteria

1. Given a value import of `api-client` in `projects/ui/`, then the build fails.
2. Given criterion 1, then the message names the file and the rule.
3. Given a **new** project added to the workspace, then the rule applies without being listed anywhere.
4. Given `projects/staff/`, then importing `api-client` is allowed.
5. Given the current codebase, then the rule passes.
6. Given `T-97`'s two-folder test, then it is deleted, not left running beside this.
7. Given the repository, then no file under `projects/*/src/` changed except that deletion.
8. `npm run build` and `ng test` green.

---

## 8. Tests

| Kind    | What it proves                                                        | Fails without the change                                                                  |
| ------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Fixture | Criteria 1, 2 — a deliberate violation in a fixture, asserted to fail | **A lint rule with no failing fixture is indistinguishable from a rule that never fires** |
| Fixture | Criterion 4 — the same import in `staff`, asserted to pass            | An over-broad rule blocks the container that is supposed to make the call                 |
| Build   | Criterion 5                                                           | Standing                                                                                  |

**The negative fixture is the whole ticket.** A rule that matches nothing passes every build.

## 11. Sub-tasks

Three, lettered, in order. Sub-tasks share the ticket's branch, **one commit each**, all in one pull
request, and **the order is the order.** There is no `feature/T-99a-...`.

**The layer shape does not apply.** This ticket writes no application code.

|       | Layer   | Deliverable                                                                | Tests in the same commit | Proves                                              |
| ----- | ------- | -------------------------------------------------------------------------- | ------------------------ | --------------------------------------------------- |
| **a** | Fixture | The deliberate violation, and the allowed import in `staff`, both asserted | Themselves               | The rule about to be written has something to catch |
| **b** | Rule    | The lint rule, folder-scoped                                               | `a`'s fixtures           | Criteria 1–5                                        |
| **c** | Removal | `T-97`'s two-folder test deleted                                           | The suite                | Criterion 6 — one enforcement, not two              |

### Why this order

**`a` first**, and for the same reason `T-57` leads with a failing test: a rule with no fixture proves
nothing, and this is the only way a reviewer can tell it fires.

**`c` last.** Deleting the old test before the new rule holds leaves a window with no enforcement.

### The risk this shape carries

**A rule that matches nothing is worse than no rule**, because it reads as coverage. `a` is not optional.
