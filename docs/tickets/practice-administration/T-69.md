**Frontend — the banner.**

|            |                                                                            |
| ---------- | -------------------------------------------------------------------------- |

| State         | Trigger                         | Renders                                                         |

| Not writable  | Practice status, any screen     | The persistent banner. **One banner, never an error per write** |

**Language and direction:** both languages, direction-aware.

## 5. Logic

**Frontend.**

**Days remaining is computed client-side from `trialEndsAt`.** `T-54` deliberately does not send a day
count — a server-computed one is stale the moment it is serialised.

**This is the one figure on this screen the client computes**, and it is a date difference, not a
judgement. Every other number comes from the response.

**Being over a limit is not an error.** A practice moved to a smaller plan keeps everyone it has
(`PRODUCT.md`). Render both numbers plainly — no red, no warning icon, no blocking.

**The banner is one persistent element, not an error on every attempted write** (`LLD-PRACTICE.md` §2.5).
A write that is refused server-side still shows its own error; the banner explains why in advance.

**Nothing here is self-service.** No upgrade control, no add-seats control. Plan and seat changes are
commercial events applied by the platform, so the screen says so rather than offering a button that
cannot work.

**No `org_id` is sent, ever.**

## 7. Acceptance criteria

1. Given an org admin visits the route, then `getSubscription` is called once and plan, status and both usage pairs render.
2. Given the call in flight, then skeleton figures render.
3. Given `trialEndsAt` is null, then no trial line renders.
4. Given `trialEndsAt` is set, then days remaining renders, computed from the instant.
5. Given `seatsUsed` exceeds `seatLimit`, then both numbers render plainly and **no error or warning styling** is applied.
6. Given a doctor, when `getSubscription` returns 403, then one message renders — not a blank screen and not a repeated call.
7. Given the header, then it carries **no action** — no upgrade, no add-seats control anywhere on the screen.
8. Given the call fails, then `ErrorMessage` renders with a working retry.
9. Given the practice is not writable, then the banner renders on **every** screen, not only this one.
10. Given criterion 9 and a doctor, then the banner still renders — it reads the session, not `getSubscription`.
11. Given the banner, then it states reading and export still work.
12. Given a refused write while not writable, then **one** banner is shown, not an error per attempt.
13. Given the practice is writable, then no banner renders.
14. Given an unknown error code, then a generic message renders and the code is logged.
15. Given Arabic, then the layout mirrors with no `left`/`right` in the section's styles.
16. Given the section's styles, then no raw hex outside `_tokens.scss`.
17. Given every new colour pair, then it is in `contrast.test.js` and passes.
18. Given the built bundle, then `subscription-section` is **not** in the initial chunk.
19. Given `ui`, then it does not import `api-client` as a value.
20. Given no request from this screen, then none carries an `org_id`.
21. `npm run build` and `ng test` green.

## 11. Sub-tasks

Six, lettered, in order. Sub-tasks share the ticket's branch, **one commit each**, all in one pull
request, and **the order is the order.** There is no `feature/T-69a-...`.

|       | Layer               | Deliverable                                                                        | Tests in the same commit                                  | Proves                                                             |
| ----- | ------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------ |
| **a** | Data                | The `staff` container holding `getSubscription`, with the 403 as a state           | `subscription-data.spec.ts`                               | The call issues once, no `org_id` is sent, and a 403 does not loop |
| **b** | Component           | The section body, both usage pairs, the trial line, the plain over-limit rendering | `subscription-section.spec.ts`                            | Criteria 1–5, 7                                                    |
| **c** | Validation          | `None.` No form, no input                                                          | —                                                         | —                                                                  |
| **d** | Errors              | The 403 state and `ErrorMessage`, plus the unknown-code path                       | Same spec                                                 | Criteria 6, 8, 14                                                  |
| **e** | Banner              | The persistent banner in the shell, sourced from the session                       | `not-writable-banner.spec.ts`                             | Criteria 9–13                                                      |
| **f** | Language and tokens | Translation keys, Arabic placeholders, colour pairs, and the route-body swap       | Chunk assertion, `contrast.test.js`, manual Arabic render | Criteria 15–18                                                     |

**`c` is `None.` and stays in the table** — an explicit `None.` reads as decided (`TICKET-TEMPLATE.md`).
**It is not a commit** — six letters, five commits.

### Why this order

**`b` before `d`**, because the over-limit rendering is the ticket's likeliest defect and it is not an
error path — putting it in the errors letter is how it acquires warning styling.

**`e` is separate and late**, because the banner is not part of this section. It lives in the shell and
must be tested on a different screen, which is only possible once the shell work is isolated from the
section work.

_Rejected: folding the banner into `b`._ It would be built inside the section, pass every spec here, and
never appear where it is needed.
