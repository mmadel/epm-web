## 2. Goal

A doctor is not shown a way into a screen that will refuse them.

## 3. Scope

### In

- The home screen's entries filtered by the caller's roles, read from the session
- The same filtered set passed to `Shell`'s `navigation` input, so a future rail inherits it
- A spec per role over the full entry set

### Out

- **Any route guard.** Hiding is presentation; the server refuses regardless — §5
- Changing any section — `T-65`–`T-69`
- The session itself — `T-81`
- Platform console navigation

## 5. Logic

**Frontend.**

**Roles come from the session service**, loaded once at start-up (`LLD.md` §12). **Not from a token
claim read client-side, not from a staff list, not from a per-screen call.**

**A person holds the union of their roles** (`PRODUCT.md`). An owner who is admin and doctor sees
everything an admin sees. There is no role that subtracts.

**Hiding an entry is presentation, not security** (`LLD.md` §12). The route stays reachable by URL, and
the screen behind it renders its own 403 state — `T-67` criterion 5 and `T-69` criterion 6 exist for
exactly that. **Removing those states because this ticket hides the entry would be wrong.**

**The filtered set is passed to `Shell`'s `navigation` input as well as rendered on the home screen**, so
restoring a rail is passing an array rather than reimplementing the rule.

## 7. Acceptance criteria

1. Given an org admin, then all four entries render.
2. Given a doctor, then Your practice and Branches render, and Staff and Subscription do not.
3. Given a receptionist, then the same two render as for a doctor.
4. Given someone holding both `DOCTOR` and `ORG_ADMIN`, then all four render.
5. Given a doctor navigating to `/staff` by URL, then the route still loads and the screen renders its own 403 state.
6. Given criterion 5, then `T-67`'s not-permitted state was not removed or bypassed.
7. Given the entries, then the same filtered set is passed to `Shell`'s `navigation` input.
8. Given the session has not resolved, then no entry renders and no partial set flashes.
9. Given roles are read, then they come from the session service and from nothing else.
10. Given Arabic, then the entries mirror with no `left`/`right` in their styles.
11. `npm run build` and `ng test` green.

## 11. Sub-tasks

Three, lettered, in order. Sub-tasks share the ticket's branch, **one commit each**, all in one pull
request, and **the order is the order.** There is no `feature/T-101a-...`.

|       | Layer        | Deliverable                                                                   | Tests in the same commit | Proves                                                                            |
| ----- | ------------ | ----------------------------------------------------------------------------- | ------------------------ | --------------------------------------------------------------------------------- |
| **a** | Data         | The role read from the session service, and the unresolved state              | `session-source.spec.ts` | Criteria 8, 9 — roles come from one place, and nothing renders before they arrive |
| **b** | Component    | The entries filtered, and the same set passed to `Shell`'s `navigation` input | `home-entries.spec.ts`   | Criteria 1–4, 7                                                                   |
| **c** | Verification | Nothing new — `T-67`'s and `T-69`'s existing specs run unchanged              | Those specs              | Criteria 5, 6: no guard was added and the 403 states still fire                   |

### Why this order

**`a` first**, because where the roles come from is the whole correctness question. A claim read
client-side renders identically and disagrees with the server the moment a role changes — and `LLD.md`
§12 puts the session behind one service for exactly this.

**`c` is not a formality.** The likeliest way to finish this ticket wrongly is to add a route guard, and
the only thing that catches it is the sections' own 403 specs still passing.

### The risk this shape carries

**One day, and the temptation is to over-deliver.** A guard, a redirect, a "you don't have access" page —
none is in scope, and each one makes a state the sections already handle unreachable.
