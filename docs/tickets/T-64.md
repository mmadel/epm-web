## 2. Goal

A platform admin fills in one form — the practice, its branches, its staff — presses submit once, and
the practice exists with every id returned.

## 3. Scope

**In**

- One route in the admin console: `/platform/onboarding`
- Three form regions: practice, branches (repeatable), staff (repeatable)
- Client-side validation for everything the server checks with a 400
- Server error codes mapped to fields
- The retry key, generated once per submission
- A seat counter, reading the chosen plan's limit from `listPlans`
- A success screen listing the created ids

**Out**

- Authentication. There is no sign-in in this release; the console runs unauthenticated locally — `T-80`
- Arabic. Internal console, English only — `PRODUCT.md`
- Editing a practice after creation — `T-41`, `0.3.0`
- Listing existing practices. There is no such route
- Changing the plan — no route exists, by decision

## 4. Contract

### The routes it calls

|                 |                                       |
| --------------- | ------------------------------------- |
| Method and path | `POST /api/v1/platform/organizations` |
| `operationId`   | `onboardOrganization`                 |
| Who may call it | Platform admin. Anyone else: 404      |
| Headers         | `Idempotency-Key` — **required**      |

And, once, when the screen opens:

|                 |                                                                                      |
| --------------- | ------------------------------------------------------------------------------------ |
| Method and path | `GET /api/v1/platform/plans`                                                         |
| `operationId`   | `listPlans`                                                                          |
| Returns         | `[{ "plan": "BASIC", "seatLimit": 5, "branchLimit": 1 }, …]`, ordered by `seatLimit` |
| Feeds           | The plan select, and the seat and branch counters                                    |

**The plan select is built from this response, not from a hardcoded list.** A plan added to the
table appears in the form without a frontend change — that is why `T-86` reads from the table.

**Both are called through the generated client** from `@mmadel/openapi-spec` (`T-91`). No
hand-written request or response type anywhere in this ticket.

### Request

```json
{
  "name": "Nile Care",
  "plan": "STANDARD",
  "clinics": [
    { "name": "Maadi", "phone": "+20221234567" },
    { "name": "Nasr City", "phone": "+20224445555" }
  ],
  "staff": [
    {
      "fullName": "Hassan Ali",
      "email": "hassan@nilecare.eg",
      "roles": ["DOCTOR", "ORG_ADMIN"],
      "specialtyCode": "CARDIOLOGY",
      "clinics": [0, 1]
    }
  ]
}
```

| Field                   | Required | Control                                            | Validation shown to the user                                 |
| ----------------------- | -------- | -------------------------------------------------- | ------------------------------------------------------------ |
| `name`                  | yes      | text                                               | Not empty                                                    |
| `plan`                  | yes      | select, options from `listPlans`                   | One must be chosen                                           |
| `clinics`               | yes, ≥1  | repeatable row group                               | At least one branch                                          |
| `clinics[].name`        | yes      | text                                               | Not empty; not equal to another row's name in this form      |
| `clinics[].phone`       | no       | text                                               | —                                                            |
| `staff`                 | yes, ≥1  | repeatable row group                               | At least one staff member                                    |
| `staff[].fullName`      | yes      | text                                               | Not empty                                                    |
| `staff[].email`         | yes      | email                                              | Valid address; not equal to another row's email in this form |
| `staff[].roles`         | yes, ≥1  | checkboxes — `DOCTOR`, `RECEPTIONIST`, `ORG_ADMIN` | At least one ticked                                          |
| `staff[].specialtyCode` | no       | select from reference data                         | —                                                            |
| `staff[].clinics`       | yes, ≥1  | checkboxes, one per branch row                     | At least one ticked                                          |

**`staff[].clinics` holds array positions, not ids.** The branches do not exist yet, so they have no
ids. The checkbox for branch row _n_ sends the integer _n_.

**Never sent:** any id, `status`, `seatLimit`, `trialEndsAt`, any timestamp.

### Response

**201 Created** — first submission. **200 OK** — same key again, same body. Both are success.

```json
{
  "organizationId": "0195e2a1-...",
  "subscriptionId": "0195e2a1-...",
  "clinics": [{ "name": "Maadi", "id": "0195e2a1-..." }],
  "staff": [{ "email": "hassan@nilecare.eg", "id": "0195e2a1-..." }]
}
```

Branches and staff come back in the order they were sent. Nothing needs re-fetching.

### Errors

| Code          | Status | Fires when                                                   | Focus and message go to                                     |
| ------------- | ------ | ------------------------------------------------------------ | ----------------------------------------------------------- |
| `EPM-REQ-001` | 400    | Malformed request                                            | The field named in the response                             |
| `EPM-REQ-002` | 400    | Unknown role                                                 | That staff row's roles                                      |
| `EPM-REQ-003` | 400    | `Idempotency-Key` missing                                    | Nowhere — this is a client defect. Log it                   |
| `EPM-ORG-001` | 400    | A branch position is out of range                            | That staff row's branch checkboxes                          |
| `EPM-ORG-002` | 409    | Two branches share a name                                    | The **second** branch row with that name                    |
| `EPM-ORG-003` | 409    | Two staff share an email                                     | The **second** staff row with that email                    |
| `EPM-ORG-004` | 422    | Unknown plan                                                 | The plan select                                             |
| `EPM-ORG-005` | 422    | Unknown speciality code                                      | That staff row's speciality                                 |
| `EPM-ORG-006` | 422    | More staff than seats allow. Carries `limit` and `requested` | The staff region header                                     |
| unknown code  | any    | A newer server than this client                              | A generic message. **Never a blank screen, never raw JSON** |

`EPM-ORG-002` and `EPM-ORG-003` should not reach the server — client validation catches both. Handle
them anyway; the server is the authority.

**The server never sends a user-facing sentence.** Its `title` field is for logs. Every message on
this screen is written in the client.

### Screen

```
┌─ Practice ─────────────────────────────────────────┐
│ Name  [___________________]   Plan [ STANDARD ▾ ]  │
├─ Branches ─────────────────────────────────────────┤
│ 1  Name [Maadi_______]  Phone [+2022...]   [remove]│
│ 2  Name [Nasr City___]  Phone [________]   [remove]│
│                                        [ add branch ]│
├─ Staff ───────────────────── 2 of 20 seats ────────┤
│ 1  Name [Hassan Ali__]  Email [hassan@...]         │
│    Roles  [x] Doctor [ ] Receptionist [x] Org admin│
│    Speciality [ Cardiology ▾ ]                     │
│    Works at   [x] 1 Maadi  [x] 2 Nasr City         │
│                                         [ add staff ]│
└────────────────────────────────────────────────────┘
                                       [ Create practice ]
```

### States

| State           | Trigger                            | What the user sees                                                                     |
| --------------- | ---------------------------------- | -------------------------------------------------------------------------------------- |
| Editing         | Default                            | Submit enabled once every required field is filled                                     |
| Submitting      | Submit pressed                     | Submit disabled and labelled "Creating…". The call writes many rows and is not instant |
| Created         | 201 or 200                         | Success panel listing every returned id, and a control to start a new practice         |
| Field error     | 400, 409, 422 with a field mapping | Submit re-enabled, focus moved to the first offending field, message beside it         |
| Plans loading   | The screen opens                   | The plan select is disabled until `listPlans` answers                                  |
| Plans failed    | `listPlans` errors                 | The form is unusable — no plan can be chosen. Show a retry, not a broken select        |
| Form error      | `EPM-ORG-006`, or an unmapped code | Submit re-enabled, message at the top of the affected region                           |
| Network failure | No response                        | Submit re-enabled. **The key is not regenerated**                                      |

Language: English only. No direction switching — internal console.

## 5. Logic

**The retry key.** Generated once, when submit is first pressed, held in component state, and sent on
every retry of that submission. Cleared only when the success panel is dismissed and a new practice is
started. A new key on retry creates a second practice.

**Branch positions.** `staff[].clinics` is derived from checkbox state at submit time, from the branch
rows' current order. **When a branch row is removed or reordered, every staff member's selection must
be recomputed in the same operation.** Model the selection as a reference to the branch row object, not
as a stored integer, and map to integers only when building the request — then reordering cannot
desynchronise it.

**Seat counter.** `staff.length` against the chosen plan's `seatLimit` from `listPlans`. Shown from
the moment a plan is chosen, not only on failure.

**Branch counter.** `clinics.length` against that plan's `branchLimit`, same rule.

**Neither counter blocks submit.** They warn; the server decides. A client-side limit that silently
disagrees with the server is worse than no limit — and the server's answer is the one that counts
(`EPM-ORG-006`).

**Changing the plan re-evaluates both counters** against the new limits, without clearing any rows.

**Computed nowhere else.** No duplicate-checking against the server, no id generation, no status.

## 6. Data

`None.` No table created, altered or dropped. No migration. This ticket adds no persistence of any
kind — the retry key lives in component state and is deliberately not stored.

## 7. Acceptance criteria

1. Given a valid form, when submit is pressed, then exactly one `POST /api/v1/platform/organizations` is sent, carrying an `Idempotency-Key`.
2. Given submit has been pressed, when the response has not arrived, then the submit control is disabled.
3. Given a 201, when the success panel renders, then it lists the organization id, the subscription id, every branch id beside its name, and every staff id beside its email.
4. Given a 200 with the same key, then the user sees the same success panel as for a 201 — no error, no warning.
5. Given the request fails and the user presses submit again, then the second request carries **the same** `Idempotency-Key` as the first.
6. Given the success panel and the user starts a new practice, then the next submission carries a **different** key.
7. Given three branch rows and a staff member ticked for rows 1 and 3, when row 1 is removed, then that staff member is ticked for the row that was 3 and the request sends position `1`, not `2`.
8. Given three branch rows and a staff member ticked for row 3, when rows are reordered, then the staff member remains ticked for the same **branch**, not the same position.
9. Given two branch rows with the same name, then submit is blocked and both rows are marked, without a request being sent.
10. Given two staff rows with the same email, then submit is blocked and both rows are marked, without a request being sent.
11. Given a staff row with no role ticked, then submit is blocked and that row's roles are marked.
12. Given a staff row with no branch ticked, then submit is blocked and that row's branch list is marked.
13. Given `EPM-ORG-006`, then the message names both `limit` and `requested` and offers two options — add a seat, or change plan.
14. Given `EPM-ORG-005`, then focus moves to the speciality control of the staff row the server named.
15. Given a code this client does not recognise, then a generic message renders and the code is logged. No raw JSON is shown.
16. No message rendered anywhere on this screen comes from the server's `title` field.
17. Every request field name and type matches the generated client's types — no hand-written interface mirrors the response.
18. Given the screen opens, then the plan select's options come from `listPlans` — a plan added to the table appears without a frontend change.
19. Given `STANDARD` is chosen and three staff rows exist, then the counter reads `3 of 20`, taking 20 from `listPlans`.
20. Given the plan is changed from `STANDARD` to `BASIC`, then both counters re-evaluate against the new limits and no row is cleared.
21. Given the staff count exceeds the plan's `seatLimit`, then the counter warns but **submit is not blocked** — the server decides.
22. Given `listPlans` fails, then the plan select is disabled and a retry is offered. No hardcoded plan list appears.

**Criterion 7 is the one that matters.** Write that test first, watch it fail against a naive
integer-storing implementation, then build the form. It is the defect `LLD-ORGANIZATION.md` calls the
most likely to ship, and it is silent — the request succeeds and the wrong people are assigned to the
wrong branch.

## 10. Stop and report

| Situation                                                                                                                           | Do not                                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `listPlans` returns numbers that contradict `PRODUCT.md` — it calls PRO "agreed per practice" while the table gives it fixed limits | Reconcile it here. Render what the route returns and report the difference; which document is wrong is a product decision |
| The speciality list has no route to read from                                                                                       | Hardcode a list. Report it                                                                                                |
| A counter tempts you to block submit at the limit                                                                                   | Block it. The server owns the rule; a client that disagrees is a form nobody can submit for a reason nobody can see       |
| A field in the generated client differs from §4                                                                                     | Change §4 to match the code. `LLD.md`: where the code disagrees with the design, the code is wrong. Report the difference |
| Any of the above tempts a change to a backend file                                                                                  | Change it. This is a frontend ticket                                                                                      |

## 11. Running it

**Prerequisites**

- Node 24, via nvm. Check `node -v` first
- Java 21 and Docker, for the backend
- `T-91` merged — the generated client comes from `@mmadel/openapi-spec@0.1.0`
- `T-86` merged — `listPlans` must answer, or the plan select is empty
- `NODE_AUTH_TOKEN` exported, for `npm ci` (`T-91` §4)

**Commands** — two terminals.

_Terminal 1, the backend:_

```
./mvnw spring-boot:run
```

_Terminal 2, the admin console:_

```
cd epm-web
npm ci
ng serve staff --port 4200
```

**What proves it worked**

1. Open `http://localhost:4200/platform/onboarding`. The three regions render: practice, branches, staff.
2. Fill in: practice `Nile Care`, plan `STANDARD`, two branches (`Maadi`, `Nasr City`), one staff member ticked for both branches.
3. The plan select lists `BASIC`, `STANDARD`, `PRO` — fetched, not hardcoded. Stop the backend and reload: the select is disabled with a retry, and no plan list appears from nowhere.
4. The seat counter reads `1 of 20` the moment `STANDARD` is chosen. Switch to `BASIC` and it reads `1 of 5` without losing a row.
5. Press create. The control disables and reads "Creating…".
6. A success panel lists the organization id, subscription id, and one id per branch and per staff member.
7. In the browser's network tab, the request carries an `Idempotency-Key` header, and `staff[0].clinics` is `[0, 1]` — positions, not ids.

**Prove the branch-removal trap is handled — criterion 7**

Add three branches. Tick a staff member for rows 1 and 3. Remove row 1. Submit and read the request
body: `clinics` must be `[1]`, pointing at the branch that was row 3 — not `[2]`, and not the row
that used to be there.

**Prove idempotency — criteria 5 and 6**

Stop the backend, press create, watch it fail. Start the backend, press create again. The second
request carries **the same** `Idempotency-Key` as the first. Then dismiss the success panel, start a
new practice, and confirm the next submission carries a **different** key.

**Tear down**

`Ctrl-C` both terminals. The practice you created stays in the database — there is no delete route,
by design. Drop the schema if you need a clean run.
