## 2. Goal

The Angular workspace generates its client from a version of the API it names in `package.json`, so
an API change arrives as a diff somebody reviewed.

## 3. Scope

**In**

- `@mmadel/openapi-spec` added as a `devDependency`, **pinned to an exact version** — no `^`, no `~`
- `.npmrc` scoped to GitHub Packages for `@mmadel`, committed at the workspace root
- `npm run generate:api` reading the specification from `node_modules`, replacing whatever `T-85` used
- The read token wired into CI
- `README` in the workspace: how to bump the API version, in three lines

**Out**

- Publishing the specification — `T-90`
- The generator itself, and the shape of the generated client. `T-85` settled both; this changes only where the input comes from
- Any screen — `T-64`
- Regenerating on every build. The generated client stays committed, as `T-85` decided

## 4. Contract

`No route is called by this ticket.`

### The package

|                |                                            |
| -------------- | ------------------------------------------ |
| Name           | `@mmadel/openapi-spec`                     |
| Version to pin | `0.1.0` — `v0.1.0` is tagged and published |
| Registry       | `https://npm.pkg.github.com`               |

**The scope is `@mmadel`, not `@epm`.** GitHub Packages requires an npm package's scope to be the
account owning the repository. `epm-service` is owned by the user `mmadel` and no `epm` organisation
exists, so `@epm/openapi-spec` is rejected with a 400 and cannot be published at all, whatever token
is used. **This does not apply to Maven** — which is why `epm-exception-lib` publishes under
`com.clinicalplatform` without trouble. It is the one part of that mechanism that does not carry
over. See §10.

```json
"devDependencies": {
  "@mmadel/openapi-spec": "0.1.0"
},
"scripts": {
  "generate:api": "openapi-generator-cli generate -i node_modules/@mmadel/openapi-spec/openapi.json -g typescript-angular -o projects/api-client/src/generated"
}
```

`.npmrc`, committed at the Angular repository root:

```
@mmadel:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

**The token is read from the environment**, never written into the file. A token committed to a
repository is a token to rotate.

**Pinned exactly.** A range means two developers generate from two specifications and neither knows.

### Authentication

|            |                                                            |
| ---------- | ---------------------------------------------------------- |
| Kind       | Classic personal access token, `read:packages`             |
| Stored as  | `PACKAGES_READ_TOKEN`, a secret on the frontend repository |
| Passed as  | `NODE_AUTH_TOKEN`, everywhere — CI and laptops both        |
| Developers | Export `NODE_AUTH_TOKEN` in their shell or shell profile   |

**`~/.npmrc` will not work, and this is not a matter of preference.** The committed `.npmrc` sets
`//npm.pkg.github.com/:_authToken` for this registry, and a project's configuration beats the user's.
A token in `~/.npmrc` is shadowed by the committed line, npm resolves the unset variable to empty,
and the registry answers **401**. One mechanism, `NODE_AUTH_TOKEN`, in every environment.

**The repository's automatic `GITHUB_TOKEN` will not work either.** It reads only its own
repository's packages, and the specification is published from a different one.

### The token guard

A `preinstall` script fails with a named message when `NODE_AUTH_TOKEN` is unset — **not a CI-only
step.** A token-less `npm ci` then fails identically on a laptop and in CI, and fails saying which
variable is missing rather than surfacing a bare 401 from the registry.

### Bumping the API version

Three steps, and they are the whole workflow this ticket exists to create:

```
npm i -E @mmadel/openapi-spec@<new version>
npm run generate:api
ng build staff && ng build patient
```

Any breakage appears at step 3, as compile errors naming the fields that changed.

## 7. Acceptance criteria

1. Given a clean checkout and a valid token, when `npm ci` runs, then `@mmadel/openapi-spec` is installed at exactly `0.1.0`.
2. Given the installed package, when `npm run generate:api` runs, then the client is generated from `node_modules/@mmadel/openapi-spec/openapi.json`.
3. Given `npm run generate:api` on an unchanged pin, then `git status` is clean — the committed client matches what `0.1.0` produces.
4. Given `package.json`, then the version is exact — no `^`, no `~`, no `latest`, no `next`.
5. Given the repository, then no file contains a token value, and the committed `.npmrc` reads `NODE_AUTH_TOKEN` from the environment.
6. Given `NODE_AUTH_TOKEN` is unset, when `npm ci` runs **on a laptop**, then `preinstall` fails naming the variable — before npm reaches the registry.
7. Given `NODE_AUTH_TOKEN` is unset, when `npm ci` runs **in CI**, then it fails the same way, with the same message.
8. Given CI, then `NODE_AUTH_TOKEN` is set from the `PACKAGES_READ_TOKEN` secret, and the automatic `GITHUB_TOKEN` is not used for this scope.
9. Given the README, then it tells a developer to export `NODE_AUTH_TOKEN` and does not mention `~/.npmrc`.
10. Given the pin is bumped to a version with a changed field name, when the client is regenerated, then `ng build` fails naming that field.
11. Given the workspace README, then bumping the API version is described in three commands.

## 10. Stop and report

| Situation                                                                  | Do not                                                                                                                                                                                                                                                  |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The registry answers **401** on install                                    | Assume the token is wrong. With the committed `.npmrc` in place, 401 means `NODE_AUTH_TOKEN` is unset or empty — npm resolved the variable to nothing. The `preinstall` guard should have caught it first; if it did not, that is a defect in the guard |
| The registry answers **404** on install                                    | Assume the package is missing. It is published — `0.1.0`, `latest`. A 404 here means the token authenticated but cannot read that repository's packages: check `read:packages`, and that it is not the automatic `GITHUB_TOKEN`                         |
| A developer's token in `~/.npmrc` is ignored                               | Debug their machine. The committed `.npmrc` shadows it by design — project configuration beats user configuration. Point them at `NODE_AUTH_TOKEN`                                                                                                      |
| `@epm/openapi-spec` appears in a document or an older draft of this ticket | Use it. The scope must be the repository owner, `@mmadel`. `@epm` is rejected with a 400 and cannot be published                                                                                                                                        |
| An `epm` organisation is created while this ticket is open                 | Rename on your own initiative. A scope change is a **different package**, not a new version — it changes the import path, the dependency and the `.npmrc` registry line together. Report it and let it be a decision                                    |
| A pre-release version looks newer than `0.1.0`                             | Pin it. `v0.1.0` is tagged; `0.1.0-SNAPSHOT.63` exists only because the tag did not, and is deletable                                                                                                                                                   |
| A version range would avoid bumping by hand                                | Use one. Bumping by hand is the point: it is the moment somebody reviews an API change                                                                                                                                                                  |
| The generated output changes when only the input path changed              | Commit it. `T-85` fixed the generator and its options — if the output moved, one of them moved too. Report what                                                                                                                                         |
| It seems simpler to regenerate on every `ng build`                         | Do it. Generation needs the registry, and a build that needs the network fails on a plane and in a locked-down runner                                                                                                                                   |

## 11. Running it

**Prerequisites**

- Node 24, via nvm. Check `node -v` first
- A classic token with `read:packages`, **exported as `NODE_AUTH_TOKEN`**. Not `~/.npmrc` — the committed `.npmrc` shadows it
- `@mmadel/openapi-spec@0.1.0` — already published, nothing to wait for

**Commands**

```
git checkout feature/T-91-generate-from-published-spec
cd epm-web
$env:NODE_AUTH_TOKEN="<token>"         # PowerShell
npm ci
npm run generate:api
ng build staff
```

**What proves it worked**

1. `node_modules/@mmadel/openapi-spec/openapi.json` exists, and its contents match the backend at `v0.1.0`.
2. `npm run generate:api` leaves `git status` clean.
3. `ng build staff` succeeds.
4. `package.json` names an exact version — open it and look.

**Prove the guard fires**

```
Remove-Item Env:NODE_AUTH_TOKEN        # PowerShell
npm ci
```

`preinstall` fails naming `NODE_AUTH_TOKEN`, and npm never reaches the registry — no 401, no stack
trace to read. Set it again and `npm ci` succeeds.

**Prove the version is doing real work**

Bump the pin to a version whose specification renames a field. Run `npm i -E`, `npm run generate:api`,
then `ng build staff`. It **fails**, naming every line that used the old name. Put the pin back.

**Show that in the pull request.** It is the whole reason the specification is versioned rather than
fetched.

**Tear down**

Nothing runs. Clear the token from your shell if it was set for this session only.
