## 2. Goal

A developer runs `ng serve`, the app calls the API on their machine, and no CORS header is needed
anywhere.

## 3. Scope

**In**

- `proxy.conf.json` at the workspace root, forwarding `/api` to the local backend
- Wired into the `serve` target of every app in `angular.json` — `staff`, `patient`, `platform`
- The generated client's `BASE_PATH` configured, and where its value comes from per environment
- One paragraph in the workspace README: run the backend, run `ng serve`, that is all

**Out**

- CORS on the backend. Deliberately — this ticket exists so it is not needed
- How deployed environments reach the API. **The proxy does not exist in a built bundle** — see §10
- Any screen. `T-64` is the first consumer
- Authentication headers on the proxied request — `T-80`
- Proxying anything but the API. No asset or websocket rules until something needs them

## 4. Contract

`No route is added or changed.` This ticket changes where requests are sent, not what is sent.

### The proxy

`proxy.conf.json`:

```json
{
  "/api": {
    "target": "http://localhost:8080",
    "secure": false,
    "changeOrigin": true,
    "logLevel": "debug"
  }
}
```

Referenced from each app's `serve` options in `angular.json`.

**The port is `8080` unless the backend says otherwise.** Confirm it rather than assuming — §10.

### The base path

| Environment             | `BASE_PATH`           | Requests go to                                   |
| ----------------------- | --------------------- | ------------------------------------------------ |
| Development, `ng serve` | **empty string**      | `localhost:4200/api/...`, forwarded by the proxy |
| Anything deployed       | Not decided — see §10 | —                                                |

An empty base path in development is what makes the proxy work: the browser sees a same-origin
request, so there is no preflight and no CORS at all.

**`BASE_PATH` is provided once, at the application's root, from the environment file.** Not passed per
call, and not read inside a component.

### What this makes unnecessary

The onboarding request carries `Idempotency-Key`, which is **not** a CORS-safelisted header. Called
cross-origin without configuration, the browser fails the **preflight** — which surfaces as a network
error rather than a rejected request, and reads like the API is down. Same origin, no preflight.

## 5. Logic

`None.` Configuration only. No component, no service, no derived value.

## 6. Data

`No table created, altered or dropped. No migration.` No browser storage.

## 7. Acceptance criteria

1. Given the backend is running and `ng serve staff` is running, when the app calls `listPlans`, then the request succeeds.
2. Given that request, when the browser's network tab is inspected, then the request URL is on `localhost:4200`, not `localhost:8080`.
3. Given that request, then **no `OPTIONS` preflight appears** — the request is same-origin.
4. Given a request carrying `Idempotency-Key`, then it reaches the backend with that header intact.
5. Given `ng serve` for `staff`, `patient` and `platform`, then all three proxy `/api` — the configuration is not wired into one app only.
6. Given the backend is **not** running, then the call fails with a proxy error naming the target, not a silent hang.
7. Given the workspace, then `BASE_PATH` is provided once at the application root and appears in no component.
8. Given the development environment file, then `BASE_PATH` is the empty string.
9. Given the README, then running the app locally is described in two commands and does not mention CORS.

## 8. Tests

| Kind                       | What it proves                                                                                   | Where                |
| -------------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| Manual, recorded in the PR | Criteria 1–4 — a screenshot of the network tab showing the `localhost:4200` URL and no `OPTIONS` | —                    |
| Config check               | Criterion 5 — all three `serve` targets reference the proxy file                                 | Lint step or review  |
| Unit                       | Criterion 7 — `BASE_PATH` is provided once and resolves to the environment value                 | `app.config.spec.ts` |

**What fails without the change:** criteria 1 to 4. Today a call to the API from `ng serve` is
cross-origin, and the onboarding request fails at preflight.

There is no automated test for a dev-server proxy — it is `ng serve` configuration and does not exist
in a test build. **The network tab screenshot is the evidence**, and criterion 3 is the one to
capture: absence of a preflight is the whole point.

## 10. Stop and report

| Situation                                                       | Do not                                                                                                                                                                                                                      |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The backend is not on `8080`, or is served under a context path | Guess. Confirm the port and whether `/api` is a context root — it decides whether `BASE_PATH` ends at the host or at `/api`                                                                                                 |
| A deployed environment needs to reach the API                   | Solve it here. **The proxy is `ng serve` only and does not exist in a built bundle.** Deployed access is a topology question — same origin behind one nginx, or CORS on the backend. Report it; it is not a frontend ticket |
| Something suggests asking the backend to allow `localhost:4200` | Ask. This ticket exists so that request is never made                                                                                                                                                                       |
| A component needs the API host                                  | Give it one. `BASE_PATH` is provided once at the root                                                                                                                                                                       |
| The proxy tempts a rule for something other than `/api`         | Add it. One rule until a second is needed                                                                                                                                                                                   |

## 11. Running it

**Prerequisites**

- Node 24, via nvm. `node -v` first
- `NODE_AUTH_TOKEN` exported, for `npm ci` (`T-91` §4)
- The backend running locally on `8080`

**Commands** — two terminals.

_Terminal 1, backend:_

```
.\mvnw.cmd spring-boot:run
```

_Terminal 2, frontend:_

```
cd epm-web
npm ci
ng serve staff
```

**What proves it worked**

1. Open `http://localhost:4200`. Open the browser's network tab **before** the app calls anything.
2. Trigger a call to `listPlans` — or hit `http://localhost:4200/api/v1/platform/plans` directly in the address bar. The three plans come back.
3. In the network tab, the request URL reads `localhost:4200/api/v1/platform/plans`. **Not `8080`.**
4. **There is no `OPTIONS` request.** That absence is criterion 3, and it is what tells you the request was same-origin.
5. Repeat with `ng serve patient` and `ng serve platform` — all three behave the same.

**Prove the failure is legible**

Stop the backend. Reload. The proxy logs a connection error naming `http://localhost:8080` and the
request fails quickly. If it hangs, or fails without naming the target, criterion 6 is not met — a
developer will read that as a broken app rather than a backend that is not running.

**Tear down**

`Ctrl-C` both terminals.
